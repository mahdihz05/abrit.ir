# R00 Task Contract — Repository Baseline and Verification Readiness

## Task ID

R00

## Status

CLAIMED

## Owner

phase1-readiness-agent

## Agent Role

Release/readiness agent with primary scope `other`. This agent owns only baseline evidence, repository-state coordination, safe verification preparation, and readiness documentation. It is not an implementation agent.

## Goal

Produce a truthful, reproducible, non-destructive Phase 1 baseline and the evidence required to decide whether R01, R02, and R03 may become `READY`.

## Context

- `docs/agent-reports/phase-1-plan-aprove.md` is the owner-designated Phase 1 plan and identifies itself internally as Version 2.
- `docs/agent-reports/phase-1-plan-v2-review.md` gives a verdict of “READY WITH CHANGES” and lists eight changes that must be reflected before feature implementation.
- The repository has pre-existing user-owned modified and untracked files, including line-ending changes and initial migrations. R00 must preserve them and must not infer permission to discard, normalize, stage, or commit them.
- The available WSL Python environment was reported unable to run Django. A supported POSIX environment must be proven before backend implementation begins.
- Verification must never write to `backend/data/abrit.sqlite3` or other repository data. Database, media, private media, cache, pytest, generated schema, build, and E2E artifacts must be contained under an approved disposable root.
- R00 is intentionally executed in the current owner-controlled worktree. The V2 review explicitly rejects creating an R00 feature worktree before readiness is established.
- Claiming R00 authorizes readiness work only. It does not authorize feature implementation, dependency installation, destructive cleanup, a commit, a new branch/worktree, migration execution against repository data, or deployment.

## Scope

1. Record the current branch, commit, worktree status, modified/untracked paths, and known line-ending risk without changing them.
2. Obtain and record explicit owner disposition for B01–B08 and G01:
   - Complete Django Admin publication boundary.
   - Read-only arbitrary Group policy and full-Group replacement on fixed-role assignment.
   - Non-enumerating lockout response and trusted client-IP/proxy rule.
   - Superuser-only user endpoints, fixed response fields, and nullable session roles.
   - Correct R02/R03/R05 migration ownership.
   - R00 execution in the current worktree.
   - R05 initial protected Admin/auth URL ownership and R13 extension ownership.
   - R02 ownership of `content/services.py`, R03 ownership of publication Admin/forms/helpers, and expanded negative tests.
3. Coordinate an owner-approved resolution or isolation strategy for existing dirty/line-ending changes. Document the strategy; do not perform destructive cleanup.
4. Identify or, only with separate dependency-installation authorization, establish a supported POSIX Python environment based on `requirements.txt` at `.runtime/phase1-venv`.
5. Define or add a safe verification wrapper only if required and authorized. It must reject unset/unsafe roots and contain all verification artifacts under `/tmp` or the CI runner's declared temporary root.
6. Run and record the unchanged backend/frontend baseline only when the supported environment and containment checks are available.
7. Produce a readiness report mapping every R00 acceptance criterion to evidence, failures, or an explicit blocker.
8. Change R00 to `IN_PROGRESS` before any permitted file modification and to `REVIEW` when the contract is satisfied. Do not mark it `DONE`.

## Constraints

- Do not modify application code or application behavior.
- Do not edit any existing initial migration.
- Do not modify, delete, move, normalize, stage, commit, or revert user-owned changes without explicit owner direction for the exact paths/action.
- Do not create or switch branches and do not create another worktree.
- Do not install dependencies without separate explicit authorization.
- Do not run migrations, tests, schema generation, builds, or E2E against repository-owned databases, media, caches, schema outputs, or build directories.
- Do not write to `backend/data/abrit.sqlite3`.
- Do not use production state, credentials, services, or deployment targets.
- Do not make R01–R18 `READY`, assign their owners, or start their work.
- If a safe baseline command cannot run, record the exact blocker instead of weakening containment rules.
- Preserve public and application files byte-for-byte unless a separately approved baseline-resolution instruction names the exact file and action.

## Acceptance Criteria

- The exact current branch, commit, dirty paths, and untracked paths are recorded without altering them.
- User-owned changes are preserved, and the owner-approved resolution/isolation decision is documented.
- B01–B08 each have a recorded approved disposition consistent with the V2 review.
- G01 records explicit approval for same-origin `/cms`, React Admin supplementing Django Admin, and fixed roles managed only by superusers.
- The `docs/IMPLEMENTATION_PLAN.md` topology conflict has an approved reconciliation decision, even if the documentation edit is assigned separately.
- A supported POSIX Python interpreter is identified and proven capable of importing the pinned backend dependencies, or the missing installation authorization is recorded as a blocker.
- Existing backend test count/baseline and Django checks are recorded when safely executable.
- Existing frontend lint, typecheck, and build baselines are recorded when safely executable.
- A safe verification path uses a unique disposable root below `/tmp` or a declared CI temporary root and rejects an unset or out-of-policy root.
- Database, media, private-media, cache, pytest, generated-schema, frontend build, and E2E artifacts are demonstrated to remain under the disposable root.
- Verification does not write to `backend/data/abrit.sqlite3`, checked-in `backend/schema.yml`, or other repository runtime data.
- No application behavior, application code, existing initial migration, dependency manifest, or lockfile changes.
- The readiness report distinguishes pass, fail, blocked, and not-run evidence without claiming unexecuted checks passed.
- R00 ends at `REVIEW` with owner `phase1-readiness-agent`; only reviewer/integration flow may mark it `DONE`.
- R01–R18 remain `BLOCKED` and `UNASSIGNED` throughout R00 execution.

## Verification Commands

Read-only repository evidence:

```bash
git branch --show-current
git rev-parse HEAD
git status --short
git diff --check
git diff --name-only
git ls-files --others --exclude-standard
```

Supported environment evidence, after any separately authorized environment setup:

```bash
test -x .runtime/phase1-venv/bin/python
.runtime/phase1-venv/bin/python --version
.runtime/phase1-venv/bin/python -c "import django, rest_framework; print(django.get_version())"
node --version
npm --version
```

Contained baseline verification, only after the wrapper exists and has validated the explicit disposable root:

```bash
ABRIT_VERIFY_DIR=/tmp/abrit-phase1-r00 scripts/check-phase1.sh --baseline
```

Post-run protection evidence:

```bash
git status --short
git diff -- backend/data/abrit.sqlite3 backend/schema.yml
```

If `scripts/check-phase1.sh` does not exist or cannot contain every artifact, do not substitute unsafe direct commands; record the check as blocked.
